
# Market Structure Logic

## 1. Raw Swing Detection

Potential swing points are identified by comparing a candle against candles before and after it.

Two parameters control the process:

### Lookback

`lookback` determines how many preceding candles are compared with the candidate pivot.

### Lookforward

`lookforward` determines how many subsequent candles must confirm the candidate.

For example:

```python
lookback = 6
lookforward = 3
```

means that a potential pivot is evaluated using six preceding candles and three subsequent candles.

Increasing these values generally produces fewer but more significant swing points.

---

## 2. Pivot Time vs Confirmation Time

A central problem in algorithmic market-structure research is that a swing occurs before the algorithm can know that it is a swing.

Consider a potential swing high.

The market may create the high at:

```text
10:00
```

but if `lookforward = 3`, several future candles must first appear before the algorithm can confirm that the 10:00 candle was actually a swing.

The implementation therefore distinguishes between several timestamps:

```text
pivot_time
raw_confirmed_time
structural_confirmed_time
```

### `pivot_time`

The candle where the actual market extreme occurred.

### `raw_confirmed_time`

The point at which enough future candles exist to identify the raw swing.

### `structural_confirmed_time`

The point at which the swing becomes a confirmed structural event according to the structural algorithm.

This distinction is important for preventing lookahead bias.

A historical chart may visually show that a swing occurred at `pivot_time`, but a backtesting algorithm must not use that swing until its corresponding confirmation time.

# Structural Swing Confirmation

Raw swings are treated as candidates rather than immediately being considered market structure.

The algorithm tracks candidate highs and lows and uses subsequent opposite-side swing information to finalize structural extremes.

The relevant functions are:

### `identify_swings`

Identifies raw swing highs and lows from clean OHLC data.

### `confirm_structural_swings`

Processes raw swing candidates and determines which candidates become structural events.

### `label_structural_swings`

Classifies confirmed structural highs and lows relative to previous structural points:

```text
HH — Higher High
HL — Higher Low
LH — Lower High
LL — Lower Low
```

These labels provide the structural state required for later BOS logic and strategy-specific filtering.

---

# Structural Events and Candle Data

Structural events are intentionally kept separate from the candle timeline.

This distinction became important because:

> one candle can confirm more than one structural event.

For example, a structural high and structural low may both receive the same `structural_confirmed_time`.

Representing structural events directly as candle rows would therefore create a one-to-many relationship between one candle and multiple structural events.

Joining those events directly into the candle DataFrame can duplicate candle rows and corrupt chronological processing.

Instead, the toolkit keeps structural events in their own event table.

The events are grouped by confirmation time:

```python
events_by_time = {
    timestamp: [event_1, event_2, ...]
}
```

The candle loop can then retrieve every structural event that becomes known on the current candle and process them deterministically.

### `build_events_by_time`

Creates this timestamp-to-events mapping.

Its purpose is **not** to prevent multiple events from occurring at the same timestamp. Multiple events are explicitly supported.

---

# Structural Labels

Confirmed structural points are classified according to their relationship with previous structural points.

For highs:

```text
Higher than previous structural high → HH
Lower than previous structural high  → LH
```

For lows:

```text
Higher than previous structural low → HL
Lower than previous structural low  → LL
```

The labels can later be used for different interpretations of structure.

This is intentionally separated from strategy-specific setup qualification.

---

# Break of Structure

The toolkit includes a flexible BOS implementation.

A bullish Break of Structure occurs when price closes above the relevant protected structural high.

A bearish Break of Structure occurs when price closes below the relevant protected structural low.

The current implementation is deliberately more general than the stricter structure-transition rules used by some SMC interpretations.
Stricter version looks like this:

```text
HL → HH → bearish break
```

or:

```text
LH → LL → bullish break
```

Such qualification can be implemented downstream using the structural labels already generated by the toolkit.

Strategy-specific BOS qualification used in the larger research project is intentionally excluded from this repository.

# Market Structure Pipeline

The main convenience function:

```python
identify_structure(...)
```

combines the structure-identification stages into a single pipeline.

```text
OHLC data
   ↓
identify_swings()
   ↓
compare_structural_swings()
   ↓
label_structural_swings()
   ↓
build_events_by_time()
   ↓
identify_bos()
   ↓
structured candle data + structural event table
```

The candle timeline remains unique and chronological throughout the process.
Structural events remain a separate representation.

# Liquidity Logic

The current liquidity implementation deliberately uses a narrow and deterministic definition.

Confirmed structural highs and lows become potential liquidity pools.

A liquidity pool becomes available to the algorithm only when its corresponding structural event has been confirmed.

This creates another important distinction between usable timestamps:

```text
pivot_time - describes where the liquidity level visually originated
```

```text
structural_confirmed_time - determines when that level may actually enter the algorithm's active state
```



This prevents historical information from being introduced before it was knowable.

---

## Liquidity Consumption

Once price breaches an active liquidity level, the pool is considered consumed and is removed from the active state.

The implementation therefore maintains a chronological collection of active structural highs and lows.

Importantly, liquidity breaches are evaluated **before new structural events from the same candle are activated**.

This avoids assuming an intrabar ordering that cannot be inferred from OHLC candles.

---

# Why Only Structural Swing Liquidity?

SMC literature and discretionary trading often describe additional forms of liquidity, including:

- Equal Highs / Equal Lows
- Clusters of nearby highs or lows
- Trend-line liquidity
- Session highs and lows
- Other visually identified areas of interest

Many of these concepts require additional subjective thresholds.

For example:

> How close must two highs be before they count as "equal"?

Without a deterministic definition, two researchers may label the same market differently.

For the current version, structural swing points were therefore selected as the primary liquidity representation because they already have an explicit algorithmic definition.

Future versions may experiment with additional liquidity models.

# Configuration

The primary structural parameters are:

```python
lookback
lookforward
```

Example:

```python
StructureConfig(
    lookback=6,
    lookforward=3,
)
```

Different parameter combinations can produce substantially different structural resolutions.

Lower values generally detect more local market structure, while higher values produce fewer and more significant structural points.

The toolkit intentionally exposes these parameters rather than claiming one universally correct configuration.
